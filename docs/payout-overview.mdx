The NadaPay Payments API gives you everything you need to move money out to a recipient — from verifying the destination corridor through to final settlement confirmation via webhook. Whether you are paying a supplier, disbursing salaries, or settling a marketplace, the same flow applies: confirm the corridor is active, register your recipient as a beneficiary, lock in a quote, and execute.

## Supported destination types

NadaPay supports three categories of payout destination. Each type has its own set of required fields on the beneficiary account.

| Type | Description | Key fields |
| --- | --- | --- |
| **Bank** | Local bank transfers and ACH-style rails | `accountNumber`, `accountName`, `networkId`, `country` |
| **Mobile money** | Mobile wallet payouts (e.g. MTN MoMo, M-Pesa) | `phoneNumber`, `provider`, `country`, `networkId` |
| **Crypto** | On-chain wallet address payouts | `chain`, `address` |

## The payout flow

Every payout — whether single or batch — follows the same ordered sequence. Skipping any step risks a failed or misdirected transfer.

<Steps>
  <Step title="Get Available Markets">
    Call `GET /api/v1/public/markets?channel=PAYOUT&isActive=true` to confirm the source→destination currency corridor is currently active. Corridor availability changes per provider, so always query this dynamically rather than assuming a static list.
  </Step>
  <Step title="Get Supported Networks">
    Call `POST /api/v1/transactions/networks` with the destination country code to retrieve the list of available payment rails and their network IDs for that country. Use the returned `code` values — do not hardcode them.
  </Step>
  <Step title="Resolve Bank Account">
    For any bank-based rail, call `POST /api/v1/transactions/resolve-bank-account` before creating the beneficiary. This confirms the account holder name and catches mismatched details before money moves.

    <Warning>
      Never skip the resolve step for bank-based payouts. A misdirected transfer caused by an unresolved account is extremely difficult to reverse.
    </Warning>
  </Step>
  <Step title="Create Beneficiary">
    Call `POST /api/v1/beneficiaries` to register the recipient. A beneficiary is a reusable profile — create it once and reuse it across many transactions.
  </Step>
  <Step title="Add Beneficiary Account">
    Call `POST /api/v1/beneficiaries/{id}/accounts` to attach the specific payout destination (bank account, mobile number, or crypto address) to the beneficiary profile.
  </Step>
  <Step title="Check Transaction Limits">
    Call `POST /api/v1/transactions/limits` with the corridor currency, country, and rail to retrieve the minimum, maximum, and daily limits. Validate your intended amount against these bounds before quoting.
  </Step>
  <Step title="Generate Quote">
    Call `POST /api/v1/transactions/quote` with the source account, destination beneficiary account, and amount. The response returns a locked `quoteId` with the finalized exchange rate and fees. Save this ID — you need it in the next step.
  </Step>
  <Step title="Execute Transaction">
    Call `POST /api/v1/transactions/execute` (or `POST /api/v1/transactions/batch-execute` for multiple payouts) with the `quoteId` and matching source/destination values. The transaction is created immediately.
  </Step>
  <Step title="Webhook confirms final state">
    Listen for the webhook event on your configured endpoint. The webhook delivers the authoritative final status — `COMPLETED`, `FAILED`, or `REVERSED` — for each transaction. Do not poll for status as a substitute for webhooks.
  </Step>
</Steps>

<Note>
  **Always resolve before adding.** For bank-based payouts, complete the resolve step and confirm the returned account name before attaching the account to a beneficiary. This is the step that catches misdirected transfers before money moves.
</Note>

## Flow summary

```
GET  /api/v1/public/markets               ← confirm the corridor is active
         ↓
POST /api/v1/transactions/networks        ← get rails for the destination country
         ↓
POST /api/v1/transactions/resolve-bank-account  ← required for bank-based rails
         ↓
POST /api/v1/beneficiaries                ← register the recipient profile
         ↓
POST /api/v1/beneficiaries/{id}/accounts  ← attach the payout destination
         ↓
POST /api/v1/transactions/limits          ← validate amount against corridor limits
         ↓
POST /api/v1/transactions/quote           ← lock in the rate and get a quoteId
         ↓
POST /api/v1/transactions/execute         ← execute (or batch-execute for multiple)
         ↓
Webhook → final state confirmed
```
