NadaPay webhooks deliver real-time event notifications to an HTTPS endpoint you control whenever something significant happens — a transaction completes, a deposit is awaiting funds, or a KYB verification finishes. Every delivery is signed with an HMAC-SHA256 signature so you can verify the payload came from NadaPay before you process it. If your endpoint does not respond with a `2xx` status, NadaPay retries the delivery automatically using exponential backoff.

<Note>
  **Sandbox vs. live webhooks:** the environment of a registered webhook is determined by the API key used to register it. Keys beginning with `np_test_...` register sandbox webhooks; keys beginning with `np_live_...` register live webhooks. Make sure you use the correct key for each environment.
</Note>

## Endpoints

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/organization/webhooks` | Register a webhook endpoint |
| `GET` | `/organization/webhooks` | List all registered webhooks |
| `GET` | `/organization/webhooks/:id` | Get details for a single webhook |
| `PATCH` | `/organization/webhooks/:id` | Update a webhook |
| `DELETE` | `/organization/webhooks/:id` | Delete a webhook |
| `GET` | `/organization/webhooks/deliveries/history` | View delivery history |
| `POST` | `/organization/webhooks/deliveries/:id/retry` | Retry a failed delivery |

## Register a webhook

### Endpoint

```text
POST /organization/webhooks
```

### Request

```bash
curl --request POST \
  --url https://core.nadapay.io/api/v1/organization/webhooks \
  --header 'x-api-key: YOUR_API_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "url": "https://your-server.example.com/webhooks/nadapay",
    "events": ["TRANSACTION.COMPLETED", "VERIFICATION.COMPLETED"]
  }'
```

## Verify the signature

Every webhook delivery includes an `X-Nadapay-Signature` header containing an HMAC-SHA256 signature. Always verify this signature before processing the event payload — it confirms the delivery originated from NadaPay and the body has not been tampered with.

```javascript
const crypto = require('crypto');

function verifyWebhook({ rawBody, signature, timestamp, secret }) {
  const signedPayload = `${timestamp}.${rawBody}`;

  const expectedSignature = crypto
    .createHmac('sha256', secret)
    .update(signedPayload)
    .digest('hex');

  return crypto.timingSafeEqual(
    Buffer.from(signature, 'hex'),
    Buffer.from(expectedSignature, 'hex')
  );
}
```

<Warning>
  **Verify the raw request body exactly as received.** Do not parse the JSON and re-serialize it before running the signature check. Parsing and re-stringifying can alter whitespace or key ordering, which will cause the signature verification to fail even for legitimate deliveries.
</Warning>

## Supported events

| Event | Description |
|-------|-------------|
| `TRANSACTION.CREATED` | A new transaction was initialized |
| `TRANSACTION.AWAITING_FUNDS` | A deposit flow is waiting for incoming funds |
| `TRANSACTION.PROCESSING` | Funds have been detected and are being processed |
| `TRANSACTION.EXECUTING` | The transaction has been sent to external banking or crypto rails |
| `TRANSACTION.COMPLETED` | The transaction settled successfully |
| `TRANSACTION.FAILED` | The transaction failed — inspect `failureReason` in the payload |
| `TRANSACTION.QUEUED` | The transaction is waiting for liquidity resolution |
| `VERIFICATION.COMPLETED` | A KYC/KYB verification process finished |

## Payload format

Every delivery shares a common envelope structure. The `data` object contains the event-specific payload.

```json
{
  "id": "delivery-uuid",
  "event": "TRANSACTION.COMPLETED",
  "environment": "LIVE",
  "timestamp": 1713289200000,
  "data": {
    "reference": "NP-ABCD-1234",
    "internalReference": "PAY-XYZ-999",
    "status": "COMPLETED",
    "sourceAmount": "1000.00",
    "sourceCurrency": "USD",
    "targetAmount": "1000.00",
    "targetCurrency": "USD",
    "totalFee": "5.00",
    "rail": "BRIDGE",
    "metadata": {}
  }
}
```

<Info>
  Amounts are represented as decimal strings (e.g. `"1000.00"`) rather than integers. Parse them accordingly in your handler.
</Info>

## Respond quickly

Return a `2xx` response as soon as you have received and validated the signature — do the heavy processing (database writes, downstream calls, notifications) in a background job or async queue. Long-running synchronous handlers are the most common cause of repeated retries.

```http
HTTP/1.1 202 Accepted
```

---

## Retry schedule

If your endpoint fails to return a `2xx` response, NadaPay retries the delivery with exponential backoff:

| Attempt | Delay after previous attempt |
|---------|------------------------------|
| 1 | 2 minutes |
| 2 | 4 minutes |
| 3 | 8 minutes |
| 4 | 16 minutes |
| 5 | 32 minutes |

After five failed attempts, the delivery is marked as permanently failed. You can trigger a manual retry at any time using `POST /organization/webhooks/deliveries/:id/retry`.

## Best practices

<Accordion title="Respond immediately, process asynchronously">
  Return `200` or `202` as soon as you validate the signature. Enqueue the event body for processing in a background worker. This prevents NadaPay from treating slow handlers as failures and avoids unnecessary retries.
</Accordion>

<Accordion title="Deduplicate using the delivery ID">
  Use the top-level `id` field as your idempotency key. NadaPay's retry mechanism can deliver the same event more than once, so your handler must be idempotent — check whether you have already processed a given `id` before acting on it.
</Accordion>

<Accordion title="Store secrets in a server-side secret manager">
  Never hardcode your webhook signing secret in application code or commit it to version control. Store it in a secrets manager (e.g. AWS Secrets Manager, HashiCorp Vault, or environment variables injected at deploy time) and read it at runtime.
</Accordion>

<Accordion title="Use HTTPS on every endpoint">
  NadaPay only delivers to HTTPS endpoints. Use a valid TLS certificate — self-signed certificates are not accepted.
</Accordion>

<Accordion title="Log key fields for reconciliation">
  Log the `id`, `event`, `timestamp`, and `data.reference` fields from every delivery. This gives you a complete audit trail for reconciling NadaPay events with your own transaction records.
</Accordion>

## Troubleshooting

<Tabs>
  <Tab title="Signature fails">
    Confirm that you are verifying the **raw request body** exactly as received — not a parsed and re-serialized version. Check that the signing secret you are using matches the one returned when you registered the webhook. Verify that you are reading the signature from the `X-Nadapay-Signature` header, not a different header.
  </Tab>
  <Tab title="Repeated retries">
    Your endpoint is not returning a `2xx` status code. Check your server logs for errors in the handler. Make sure the endpoint is publicly reachable and not blocked by a firewall or auth layer. Return `202 Accepted` as early as possible and move processing to a background job.
  </Tab>
  <Tab title="Duplicate events">
    This is expected behavior — NadaPay can deliver the same event more than once due to retries. Use the top-level `id` field as a deduplication key and skip processing if you have already handled that delivery ID.
  </Tab>
</Tabs>
